# 决策记录

> 追加式更新。推翻旧决定时新增一条并注明「取代 #N」，不改写历史。
> 状态快照见 `docs/STATUS.md`。

## 1. 纯前端、零后端

**决定**：不做服务器，全部逻辑在浏览器；数据存 `localStorage`，换设备靠导出/导入 JSON；
费率跳档提醒用 `.ics` 日历文件代替推送。

**理由**：免备案、零成本、永久在线；持仓数据不出浏览器本身是卖点；没有后端就没有
「你在收集用户持仓」的想象空间。

**被否**：云同步 + 账号（要后端）；邮件/微信推送（要服务端定时任务）。

## 2. 不做建议者，做执行器

**决定**：所有规则由用户设定，工具只负责算和提醒。文案永远是「按你设定的规则」。

**理由**：给具体买卖建议属于基金投顾业务，需牌照；且「该减多少」没有客观答案，
给了数字就要为结果负责。规则归用户，责任归属才清晰。

**被否**：AI 推荐减仓比例；估值分位择时。

## 3. 抄平台费率，不做账本

**决定**：不记录交易流水，让用户从卖出页抄「本次赎回费率」；内置 A/C 分档表只作估算兜底。

**理由**：真实赎回费按「先进先出 + 按笔计费」，精确计算要还原完整流水，录入成本远超收益。
平台已经算好了，抄一个数更准。账本是最后手段，不是起点。

**被否**：完整流水账本；OCR 对账单。

## 4. 推荐值 = 已触发规则的中位数

**决定**：每条规则给出自己的减仓比例，取中位数并展示区间与每条算式。

**理由**：没有哪条规则更权威，中位数对极端值不敏感；区间能暴露规则之间的分歧，
比加权平均的「假精确」更诚实。

**被否**：加权平均（权重无从定义）；取最大值（过于激进）。

## 5. 流派用「名字 + 思想来源」，不用真人姓名

**决定**：七个流派（落袋为安 / 趋势跟随 / 分批收割 / 仓位纪律 / 本金落袋 / 定投止盈 / 严格止损），
每个带一句思想来源，不叫「某某流派」。

**理由**：多数投资大师没有机械化减仓规则，硬套失真；真人姓名做功能命名有背书与侵权风险；
一旦亏钱会同时归因到那个人和产品。用户指定要做流派预设，本方案是折中。

**被否**：直接用「巴菲特流派」「索罗斯流派」（用户最初设想）。

## 6. 只做场外开放式基金

**决定**：支持场外开放式、ETF 联接、LOF 场外份额、A/C 类、QDII（费率须抄平台）。
不做场内 ETF、股票、货币基金、银行理财。

**理由**：基金是唯一「净值单一、费率规则清晰、没有盘中价格」的品类，正好是工具成立的前提。
扩到股票要重做费用与时点模型。

## 7. 三页结构：持仓 / 结果 / 规则

**决定**：底部标签栏 + 左右滑动，一屏一件事；输入页尽量一屏装下。

**理由**：用户反馈「下滑太乱、没有主体感」。已知代价：10 个字段在 667px 小屏仍需滚动，
这是物理限制；通过「默认值 + 可选字段折叠」缓解，不为凑一屏删字段。

## 8. OCR：tesseract 自托管 + 版面配对 + 分带/框选

**决定**：用 tesseract.js（chi_sim）在浏览器本地识别；引擎与模型自托管；
用坐标做「标签 → 数值」配对；整图失败时切 6 个重叠横带逐带识别并按置信度合并；
另提供手动框选。

**理由**：jsdelivr 在国内不可用，必须自托管；基金持仓页是「标签一行、数值一行」的三列网格，
按文字顺序配对必然张冠李戴，必须用 x/y 坐标；tesseract 会把大面积色块当图片跳过，
裁成条带才能识别（实测：整图 0 字段 → 裁顶部 46% 后 4/4 全对）。

**被否**：云 OCR（百度/腾讯）——准确率更高但要后端代理藏 key，破坏纯前端定位。

## 9. OCR 结果覆盖式写入，绝不静默填入

**决定**：识别结果先列出，用户点「填入表单」才写入；写入时**未识别的字段一律清空**。

**理由**：曾出现「旧示例数据（净值 2.0459 / 天数 107）留在表单里，看起来像识别出来的」，
比识别失败更危险。用户明确要求别让底字冒充数据，输入框也不再用示例数字做 placeholder。

## 10. 先不买域名

**决定**：先用 Cloudflare Pages 免费二级域名 `jiancang.pages.dev`。

**理由**：托管免费，域名（约 ¥100/年）是可选项；产品未验证前不付年费。
项目名必须叫 `jiancang`，否则要同步改 `index.html` 的 `og:url` / `og:image`。

## 11. 标准化 = 一致性与可验证，不重做视觉

**决定**：走 B「标准产品」路线，保留蓝白视觉，收敛设计令牌、统一按钮/圆角/状态，
补齐引导、帮助、隐私、版本、PWA、CI 等「正式工具该有的外壳」。

**理由**：现有界面底子不差，缺的是一致性与信任信号；换风格重做既慢又丢已有辨识度。

**被否**：独立营销落地页（工具本身就是落地页）；大 UI 框架（包体和风格都不划算）。

## 12. 解耦：core / app / pages / shell / ui 五层

**决定**：算法留在 `core/`；状态与动作收进 `useAppState`；三页只做组装；
外壳与通用原语独立。页面顺序改为「持仓 → 规则 → 结果」。

**理由**：用户明确说标准化之后还会频繁改功能、页面甚至大改。把「计算」「状态」
「页面」「外壳」「视觉」拆开，改一层不用动其他层；`core/` 一行未改就通过了全部旧测试，
是这个拆分有效的证据。

**被否**：继续把状态堆在 `App.tsx`（每改一页都要碰同一坨逻辑）。

## 13. 示例数据合成化，且必须显式标识

**决定**：演示表单改用合成数字；`?demo=1/2` 与「载入示例」都显示「示例数据」横幅，
分享卡片打「示例数据」水印。

**理由**：真实持仓数据（哪怕是开发者的）没有理由随产品公开；示例数据不标识，
会被当成真实持仓转发，违背「数据只在本机」的信任叙事。

## 14. PWA 手写 Service Worker，而不是引 workbox

**决定**：自写约 80 行 SW：外壳预缓存、导航 network-first、OCR 资源首次用时再缓存；
图标用 Pillow 生成静态 PNG。

**理由**：逻辑简单、可控、零运行时依赖；13MB OCR 资源不能在安装时预取。
代价是版本升级要手动改 `VERSION`，换来的是没有构建期魔法。

## 15. 文案从「推荐」改为「按规则应减」

**决定**：结果页主标签、分享卡片统一写「按规则应减」；「恢复推荐」改为「恢复规则值」。

**理由**：工具定位是执行器，不是建议者。「推荐」二字会把规则中位数读成产品意见，
与硬约束和免责声明互相打架。
